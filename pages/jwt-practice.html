Практика работы с JWT

В предыдущих главах мы разобрали теорию: что такое JWT, зачем он нужен и как устроен изнутри. Теперь пришло время перейти к практике. В этой главе мы подробно рассмотрим процесс аутентификации с использованием JWT, посмотрим примеры кода и разберёмся, как правильно хранить токены в клиентских приложениях.

Процесс аутентификации с JWT

Типичный сценарий использования JWT в веб-приложении выглядит следующим образом:

  1. Пользователь отправляет учётные данные. Клиент (браузер или мобильное приложение) отправляет на сервер логин и пароль через защищённое HTTPS-соединение.
  2. Сервер проверяет данные. Бэкенд сверяет полученные данные с записями в базе данных. Если логин и пароль верны — переходим к следующему шагу.
  3. Сервер создаёт JWT. Бэкенд генерирует токен, помещая в Payload идентификатор пользователя (sub), его роль (role), время выпуска (iat) и время истечения (exp). Затем токен подписывается секретным ключом.
  4. Сервер отправляет токен клиенту. JWT возвращается в теле ответа (обычно в формате JSON: {"token": "eyJhbG..."}).
  5. Клиент сохраняет токен. Браузер или приложение сохраняет токен в локальном хранилище (localStorage, sessionStorage или cookie).
  6. Клиент отправляет токен с каждым запросом. При обращении к защищённым эндпоинтам API токен передаётся в заголовке Authorization: Bearer <token>.
  7. Сервер проверяет токен. Бэкенд извлекает токен из заголовка, проверяет его подпись с помощью секретного ключа и убеждается, что срок действия (exp) не истёк.
  8. Сервер выполняет запрос. Если токен валиден, сервер извлекает данные пользователя из Payload и выполняет запрошенное действие.

Примеры кода

Рассмотрим практические примеры работы с JWT на разных этапах.

Создание токена на сервере (Node.js)

Пример генерации JWT с использованием популярной библиотеки jsonwebtoken:

const jwt = require('jsonwebtoken');

const secretKey = 'your-super-secret-key';

function generateToken(user) {
    const payload = {
        sub: user.id,
        name: user.name,
        role: user.role,
        iat: Math.floor(Date.now() / 1000),
        exp: Math.floor(Date.now() / 1000) + (60 * 60) // 1 час
    };
    
    return jwt.sign(payload, secretKey, { algorithm: 'HS256' });
}

Проверка токена на сервере

Пример middleware, который проверяет токен в каждом запросе:

function authenticateToken(req, res, next) {
    const authHeader = req.headers['authorization'];
    const token = authHeader && authHeader.split(' ')[1];
    
    if (!token) {
        return res.status(401).json({ error: 'Токен не предоставлен' });
    }
    
    jwt.verify(token, secretKey, (err, user) => {
        if (err) {
            return res.status(403).json({ error: 'Недействительный токен' });
        }
        req.user = user;
        next();
    });
}

Отправка токена с клиента (JavaScript)

Пример запроса к защищённому API с использованием fetch:

async function fetchUserData() {
    const token = localStorage.getItem('jwt_token');
    
    const response = await fetch('https://api.example.com/user/profile', {
        method: 'GET',
        headers: {
            'Authorization': `Bearer ${token}`,
            'Content-Type': 'application/json'
        }
    });
    
    if (!response.ok) {
        throw new Error('Ошибка авторизации');
    }
    
    return await response.json();
}

Где хранить JWT на клиенте?

Выбор места хранения токена — один из ключевых вопросов безопасности. Рассмотрим два основных варианта:

1. localStorage / sessionStorage

  • Плюсы: простота использования, токены не отправляются автоматически с каждым запросом (защита от CSRF).
  • Минусы: уязвимость к XSS-атакам. Если злоумышленник внедрит вредоносный JavaScript на страницу, он сможет украсть токен.

2. HttpOnly Cookie

  • Плюсы: недоступны для JavaScript (защита от XSS), отправляются автоматически.
  • Минусы: уязвимость к CSRF-атакам (нужна дополнительная защита), сложнее работать с кросс-доменными запросами.

Рекомендация: для большинства современных SPA-приложений оптимальным выбором является хранение в httpOnly cookie с флагами Secure и SameSite=Strict.

Refresh Token: обновление токена

Поскольку JWT имеет ограниченный срок жизни (обычно 15 минут — 1 час), возникает вопрос: как пользователю оставаться в системе, не вводя пароль каждый раз? Для этого используется механизм Refresh Token.

Refresh Token — это отдельный токен с длительным сроком жизни (например, 7 дней или 30 дней), который хранится на сервере или в безопасном хранилище. Когда Access Token (основной JWT) истекает, клиент отправляет Refresh Token на специальный эндпоинт и получает новую пару токенов без повторного ввода пароля.

Такой подход сочетает безопасность короткоживущих токенов с удобством долгой сессии для пользователя.

Частые ошибки при работе с JWT:
  • Использование слабого секретного ключа. Ключ должен быть длинным (минимум 256 бит для HS256) и случайным.
  • Отсутствие проверки срока действия (exp). Всегда проверяйте, не истёк ли токен, на сервере.
  • Хранение чувствительных данных в Payload. Помните: Payload только закодирован, любой может его прочитать.
  • Использование алгоритма none. Некоторые библиотеки позволяют создать токен без подписи — это критическая уязвимость.
  • Передача токена через URL. Токен может попасть в логи сервера и историю браузера. Используйте только заголовок Authorization.

Краткое резюме

Практическое использование JWT включает создание токена на сервере после успешной аутентификации, передачу его клиенту и проверку подписи при каждом запросе к защищённым ресурсам. Правильный выбор места хранения токена и использование Refresh Token позволяют создать безопасную и удобную систему аутентификации.

Теперь, когда мы полностью разобрались с JWT, давайте перейдём к другому важному стандарту — протоколу OAuth 2.0, который решает задачу авторизации без передачи пароля.
